# JFrog OIDC for serverless — project notes for Claude Code

Short-lived JFrog tokens for Cloud Run (services, jobs, functions), Azure Container Apps and Azure Functions (Flex Consumption, Premium/Dedicated, Functions on ACA), and Knative services (OpenShift Serverless or any Knative cluster), using OIDC token exchange. Nothing long-lived is stored anywhere.

We are now building **the console**: a local web UI that configures, simulates and verifies this for a target. The full spec is in `docs/console-spec.md`; read it before starting any milestone. Record progress in `docs/progress.md`.

## Layout

- `client/` — `jfrog_oidc`, a stdlib-only Python client: identity sources (GCP, Azure, ADO, file), the exchange with caching, helpers and a CLI.
- No pull path and no rotator on any cloud: no registry username/password anywhere. Images come in at build time: each build-deploy pipeline pulls from JFrog with its OIDC token and pushes to that stack's own registry (AR on GCP, ACR on Azure), and the platform pulls with its own identity. At runtime the app exchanges its cloud identity for a JFrog token.
- `terraform/modules/` — `jfrog-oidc`, `azure-identity` (Entra audience app only). `terraform/stacks/<serverless|kubernetes>/<gcp|azure>/<stack>` holds the deployable root configs, one folder per stack, Serverless and Kubernetes and each cloud in their own tree: `aks-cluster` and `gke-cluster` (test clusters, OIDC issuer on), `gcp-pipeline-identity` and `azure-pipeline-identity` (each cloud's own ADO trust: its own service connections `jfrog-oidc-<cloud>-build/-setup` (GCP's only issue the OIDC token; the GCP pipelines reference them from a skipped `AzureCLI@2` task and never sign in to Azure), WIF or federated credentials, its pipeline variable group `jfrog-oidc-<cloud>-<env>`, its state store; nothing in JFrog; clouds share nothing; no AWS). Infrastructure never touches JFrog: after it exists, `terraform/stacks/oidc/<cloud>/<cloud>-jfrog-trust` creates that cloud's JFrog integration `ado-<org>-<cloud>`, the `ado-build`/`ado-setup` mappings, the variable group `jfrog-oidc-<cloud>-<env>-jfrog` (`JFROG_URL`, `JFROG_OIDC_PROVIDER`; read only by build-deploy and onboarding pipelines, never stack-setup) and, on GCP, the console operator; `terraform/stacks/oidc/azure/aks-jfrog-trust` (after `aks-cluster`, its own stack-setup pipeline `pipelines/oidc/azure/aks-jfrog-trust/` on `pipelines/templates/azure-oidc-stack-setup.yml` and `pipelines/scripts/oidc-stack.sh`, registered with its ADO environment and approval by `azure-jfrog-trust`, never by the pipeline identity; JFrog token from the setup connection via `ado-setup`) trusts the cluster's issuer, maps `jfrog/jfrog-provider-sa` and has Argo CD install the credential provider chart on nodes labelled `credentialsProviderEnabled`. One stack per serverless workload type, each independent and standing only on its cloud's pipeline identity: GCP `gcp-cloud-run` (job), `gcp-cloud-run-service`, `gcp-cloud-run-function`; Azure `azure-container-apps` (job), `azure-container-app`, `azure-functions-aca`, `azure-functions-premium`, `azure-functions-flex`, `azure-web-app` (App Service, Linux or Windows, Python/Java/.NET code: no registry; build-deploy resolves pip/Maven/NuGet through JFrog with `jfrog_oidc pip|mvn|dotnet` and zip/jar-deploys) (the Azure ones on `terraform/modules/azure-workload`: own resource group, identity, registry/environment/storage as needed). Never deploy two workload types in one apply or one pipeline run. Stacks hold no target values: their inputs are filled in on the Infrastructure page.
- `apps/` — workload images and functions that use the client: `artifact-reader` (job for Cloud Run and Container Apps), `cloud-run-service`, `cloud-run-function`, `cloud-run-worker-pool`, `azure-function`, `web-app` (App Service: `java` and `dotnet` with the same endpoints as `cloud-run-service`, which is also the Python web app).
- `pipelines/` — Azure DevOps pipelines (the only CI/CD). Infrastructure and JFrog OIDC are separate at pipeline level: infra stack-setup runs use `<cloud>-stack-setup.yml` → `scripts/terraform-stack.sh` → `scripts/ado-login.sh` (cloud sign-in only: no JFrog group, vars file, token or provider); JFrog OIDC stack runs use `azure-oidc-stack-setup.yml` → `scripts/oidc-stack.sh` → `scripts/oidc-login.sh`; build-deploy and onboarding read the JFrog group and `vars/<cloud>-<env>-jfrog.yml` (repository names). Never put JFrog into an infra template, script or vars file. One folder per serverless workload stack, `pipelines/serverless/<cloud>/<stack>/` with `stack-setup.yml` (plan → approval on the ADO environment `<stack>-<env>` → apply, or destroy) and `build-deploy.yml` (builds and rolls out that one workload). Each is a thin file over `pipelines/templates/<cloud>-stack-setup.yml` / `<cloud>-build-deploy.yml`; never add a pipeline that handles two stacks or two workload types. `<cloud>-workload-onboard.yml` applies and wires the workspaces the console proposes by pull request (`terraform/workspaces/<cloud>_*`). Every job authenticates with its service connection's OIDC token; ADO settings per cloud in `pipelines/vars/<cloud>-<env>.yml`; target values in the ADO variable group `jfrog-oidc-<cloud>-<env>`, written by that cloud's pipeline identity stack. `pipelines/delivery.json` holds only the ADO repo; pipeline identities and state backends come from the pipeline identity outputs.
- `console/` — the Serverless console, per the spec. Clouds: GCP, Azure and Knative (`steps/openshift.py`, spec §12; works on any cluster through a kubectl context). Knative is runtime path only. No AWS.
- `setup_console/` — two portal mounts of one server, each with its own scope: Infrastructure at `/setup` (scope `infra`) deploys and destroys **test infrastructure** where none exists yet (each cloud's pipeline identity, its workload-type stacks, the `gke-cluster`/`aks-cluster` stacks); JFrog OIDC at `/oidc` (scope `oidc`) only the JFrog OIDC stacks (`<cloud>-jfrog-trust`, run here like the pipeline identity stacks; `aks-jfrog-trust` in ADO). Each mount answers 404 for the other's stacks and runs; they share only the run engine. Runs has separate Infrastructure and JFrog OIDC tabs. Workload and cluster stacks run in ADO (Deploy queues the stack-setup pipeline, Approve answers its approval); pipeline identity stacks run here. Plan → approve the plan's sha256 → apply; destroy also needs the stack name typed. Inputs: a form generated from each stack's `variables.tf` (live project/subscription pickers), saved to `.console/setup/<env>/<stack>.tfvars.json` (outside git) and passed with `-var-file`; remote state is `-backend-config` derived from that cloud's own pipeline identity inputs only (`<gcp_project_id>-tfstate`, `st<ado_org>tfstate`); form prefill never crosses clouds or kinds. The page has two independent sections, Serverless (pipeline identity stacks and one row per workload type) and Kubernetes (`gke-cluster`, `aks-cluster`): the cluster stacks keep their state in their cloud's pipeline identity store and deploy through their own stack-setup pipelines (`pipelines/kubernetes/<cloud>/<stack>/`). Clouds are completely separate, as in production: never add a stack, variable group, vars file or JFrog integration shared by two clouds. The stack-setup pipelines take the same JSON as `inputs`/`state` parameters. Never write target values into `terraform/`. In production the targets already exist and only the two configure consoles run; Setup is never needed there.
- `portal/` — one UI for both consoles (`docs/merge-plan.md`): Serverless (`console/`) at `/serverless`, Kubernetes (`kcp_console/`) at `/k8s`. It only routes by prefix; the two consoles keep separate Python packages, stores, runs and gates, but the browser is ONE UI: `/k8s` pages import `/serverless/static/{core,time,logview}.js` (session, api, h/fill/help, times, log table). Change a UI piece once, there, never a KCP copy. Settings (`/settings`, `portal/connections.py`) holds the sign-ins: Google Cloud and Azure log in from the page into `.console/connections/` (or use the machine's login); ADO values override `delivery.json`; the JFrog admin token stays in memory only.
- `kcp_console/` — the KCP console, served only by the portal at `/k8s` (no standalone entry point): the AKS kubelet credential provider sibling (spec `docs/kcp-console-spec.md`, progress `docs/kcp-progress.md`). Same rules as `console/`. On AKS it never installs or removes the provider (that is the `aks-jfrog-trust` pipeline): Set up and Tear down are refused; it verifies and proves. Otherwise, state-changing az/kubectl/helm and JFrog writes run only as a direct plan (`kcp_console/direct.py`, AZURE.md Option B) or an ADO pipeline run, after a DryRun and an explicit, hash-bound approval. Ad-hoc reads stay read-only (`k8s.py`).

## Commands

```bash
# client tests
cd client && PYTHONPATH=src python -m unittest discover -s tests -v
# console tests (once console/ exists)
PYTHONPATH=client/src:. python -m unittest discover -s console/tests -v
# simulation scenarios vs expectations (M1+), including Knative
PYTHONPATH=client/src:. python -m console.sim check-all
PYTHONPATH=client/src:. python -m console.sim run happy-openshift-knative
# terraform (needs network to the provider registry)
for s in terraform/stacks/*/*/*/; do terraform -chdir=$s init -backend=false && terraform -chdir=$s validate; done
terraform fmt -recursive -check terraform/
# run the console (M2+)
PYTHONPATH=client/src:. python -m console
# KCP console: tests, simulator, run (replay fixtures)
python3 -m unittest discover -s kcp_console/tests -t .
python3 -m kcp_console.sim check-all
PYTHONPATH=client/src:. python3 -m portal --kcp-fixtures kcp_console/tests/fixtures/sandbox
# portal: both consoles on one port, Serverless at /serverless, Kubernetes at /k8s
PYTHONPATH=client/src:. python3 -m unittest discover -s portal/tests -t .
PYTHONPATH=client/src:. python -m portal
# Setup console (test infrastructure): tests
PYTHONPATH=client/src:. python3 -m unittest discover -s setup_console/tests -t .
# KCP JFrog access: no stored token and nothing to set; the console reads its operator identity from gcp-jfrog-trust's console_operator_env output
```

## Rules

- **Stdlib only** in `client/` and `console/`. No pip dependencies and no JS build step. The UI is vanilla ES modules with no CDN.
- **Never print, log, store or return a token.** That covers JFrog access tokens, identity JWTs, `JFROG_ACCESS_TOKEN`, secret values and function keys. Route every log and SSE line through `console/redact.py`. If you add a log path, add it to the redaction test.
- **Simulation runs the real code.** Do not mock `jfrog_oidc` inside the simulator; emulate the HTTP endpoints they call. If the simulator needs a hook, add a seam to the real code (as `clock=`/`sleep=` already are) and keep the default behaviour identical.
- **No cloud or JFrog changes without approval.** `terraform apply`, `gcloud … update/deploy/execute`, `az … update/set/start` and JFrog writes happen only behind the console's approval gates. During development, do not run them yourself against real accounts unless I ask in the session.
- **Terraform is the source of truth** for identity and the JFrog side. The console generates JSON-syntax workspaces (`main.tf.json`) that call the modules. Never string-template HCL.
- **Subprocesses:** argv lists only, never `shell=True`, always a timeout, and always through `console/shell.py`.
- **Server:** bind to 127.0.0.1, require the session token, check Host/Origin, set a strict CSP.
- **Tests first** for every step module. Use recorded fixtures for gcloud/az JSON and a fake `terraform` script in `console/tests/fixtures/`. Unit tests never need cloud access.
